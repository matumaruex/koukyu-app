# 公休表の生成処理・スマホ画面

CP-SATで期間全体を組み、独立した検査を通った表だけを返します。新しいスマホ画面は `public/`、公開用の計算窓口は `api/schedule.py` です。旧ブラウザ保存領域は上書きしません。開発開始時の基準コミットは `dabcc76d3c63c01fedfc0fcd6753b58f8d2bc4a9` です。

## このPCで試す

新スマホ画面は `python -m solver.app_server` で起動し、`http://127.0.0.1:8766/` を開きます。以下は旧検証室の手順です。

`起動.ps1` をPowerShellで実行し、表示される `http://127.0.0.1:8765/` を開きます。起動中のウィンドウを閉じると終了します。

画面でテストケースを選び「条件を読み込む」→必要に応じて公休・夜勤・希望休などを変更→「この条件で検証する」。条件と結果はJSONで保存できます。本番アプリの書き出しも読み込めます。対象月を選んでから読み込むと、その月の希望休と、前期の末尾7日分があれば取り込みます。既存の当期勤務は固定扱いにせず、白紙から再生成します。

期間を変更すると履歴・固定勤務は解除されます。旧期間の希望休が残っていれば、日付を修正するまで計算できません。

## 守る条件

- 期間は指定月16日〜翌月15日。1人1日1区分。
- 毎日夜勤1人。夜勤の翌日は必ず明け。前日に夜勤がなければ明けは不可。
- 朝7:00・昼10:00・夕17:45は4人以上。日曜の朝昼に限り、月3日まで3人以上へ緩和可。朝昼を両方減らしても同じ日なら1日と数える。
- 希望休は必ず公休。明けで代用しない。
- 公休は各人の設定日数以上。
- 余分な公休＝実際の公休日数−設定日数。その最大差は初期設定1日以内、画面で完全同数（0日）も選択可。勝手な緩和はしない。
- 夜勤資格、金土日の夜勤不可、A残の可否、パートの個別勤務時間を尊重。
- A残は月6回以内、連日不可。前期最終日との連続も確認。
- 連勤上限を尊重。明けは旧アプリと同じく連勤を区切る。`allowConsecutivePlus1`が真なら上限+1を当期中に1回だけ許可。
- パートの週上限は月曜始まり。前期履歴の同じ週も含む。
- `locked` の固定勤務を保持。

旧検証室は職員の形態・勤務時間・連勤+1設定を読み込んだデータから使用します。新スマホ画面では職員設定を編集できます。

## 公平さと品質の優先順位

必須条件を守った表の中で、(1)余分な公休の最大差、(2)余分な公休の総数、(3)A/B回数差・夜勤回数差・A残回数、の順に小さくします。(1)を犠牲にして(2)(3)だけを改善しない重み付けです。例：1人が+2日なら、可能な限り全員+2日に揃えます。

最適化が時間切れでも検査済みの表があれば返しますが、「すべてのバランスが最良」とは表示しません。公休超過の差が0なら、公平さの差についてはそれ以上小さくできません。勤務日数を減らしすぎない最適性とは別です。

## 判定の意味

|結果|意味|
|---|---|
|OPTIMAL|登録したモデルの必須条件を満たし、指定した評価値の最適性も確認|
|FEASIBLE|必須条件と独立検査を満たすが、評価値の最適性は未確認|
|INFEASIBLE|入力モデルの条件が同時に成立しないことを確認。表は返さない|
|UNKNOWN|時間内に解または不成立の証明を得られなかった。表は返さない|
|INVALID_INPUT|形式や範囲が不正。計算しない|
|VALIDATION_FAILED|生成後の独立検査で違反を検出。表は返さない|

`conflictGroups`は十分な矛盾条件群で、最小の原因集合ではありません。現状は条件が多数列挙される場合があり、「どこを変えればよいか」の最小変更提案は未実装です。

## 期間境界と未確認事項

`history`は各職員の前期末尾7日分（古い順）。未入力の職員は試験上のみ全休と仮定します。全員分がなければ `PERIOD_ONLY` であり、実際の勤務との境界の合格とは扱いません。不成立もこの仮定の下での判定です。

`carryForward`に末尾7日と、最終日が夜勤なら翌期初日に必要な明けを返します。翌期の全条件まで先読みして成立を保証するものではありません。

現場の完成済み勤務表との照合はまだです。休憩中の人数、全時刻の人数、資格別配置、遅番翌日の早番禁止、労働時間・契約別の上限等は既存ルールにないためモデル化していません。明けを連勤に数えるか、公平さを全職員で比較してよいかも、実運用前に確認が必要です。

## 再現手順（開発用）

Python 3.12 / OR-Tools 9.15.6755。新しい環境では以下を実行します。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r solver/requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s solver/tests -v
.\.venv\Scripts\python.exe -m solver.benchmark
.\.venv\Scripts\python.exe -m solver.server
```

CLIは `python -m solver.engine input.json --output result.json --seconds 15`。`--feasibility-only`は勤務バランスの最適化を省きますが、公平さの上限を含む必須条件と独立検査は省きません。

入力は既存の職員配列に `year`, `month`, `requests`（1始まりの期間日番号）、任意で `locked`（職員ID→期間日番号→シフト）、`history`、`maxExtraOffSpread` を追加したものです。検証時に生成される `results/case-*.json` の `input` を参照してください。個別の結果データはGitHub・公開サイトへ含めません。

公開版は `public/` のスマホ画面から `api/schedule.py` を呼び出します。職員名を除いて計算条件を送信し、サーバーに表は保存しません。通常の作成は上限60秒で、15秒たち、かつ最初の表から10秒たった時点で止めて返します（`adaptive: true`。それより前に最適・不成立を証明できればその時点で返す。結果の `stopRule` に止めた理由と最初の表までの秒数）。追加計算は60秒で、独立検査済みの表を初期候補とし、時間切れなら元の表を保持します。表がないまま時間切れになった後の再計算は、`seed`（1〜1000）を変えて探す順番を変えます。検証室は引き続きPC内で動きます。公開版と同じ画面の確認は `python -m solver.app_server`（8766番）です。

旧ブラウザデータは新しい保存領域に引き継ぎます。バックアップ読み込み・手直し・条件変更後は再検査が必要です。前期7日未入力は必ず下書き扱い。公開APIは1回最大60秒、40人、入力400KBに制限します。認証はありません。アクセス増加時には利用制限の追加が必要です。
