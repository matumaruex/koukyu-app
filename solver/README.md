# 公休表の生成処理・スマホ画面

CP-SATで期間全体を組み、独立した検査を通った表だけを返します。新しいスマホ画面は `public/`、公開用の計算窓口は `api/schedule.py` です。旧ブラウザ保存領域は上書きしません。開発開始時の基準コミットは `dabcc76d3c63c01fedfc0fcd6753b58f8d2bc4a9` です。

## このPCで試す

新スマホ画面は `python -m solver.app_server` で起動し、`http://127.0.0.1:8766/` を開きます。以下は旧検証室の手順です。

`起動.ps1` をPowerShellで実行し、表示される `http://127.0.0.1:8765/` を開きます。起動中のウィンドウを閉じると終了します。

画面でテストケースを選び「条件を読み込む」→必要に応じて公休・夜勤・希望休などを変更→「この条件で検証する」。条件と結果はJSONで保存できます。本番アプリの書き出しも読み込めます。対象月を選んでから読み込むと、その月の希望休と、前期の末尾7日分があれば取り込みます。既存の当期勤務は固定扱いにせず、白紙から再生成します。

期間を変更すると履歴・固定勤務は解除されます。旧期間の希望休が残っていれば、日付を修正するまで計算できません。

## 守る条件

- 期間は指定月16日〜翌月15日。1人1日1区分。
- 毎日夜勤1人。夜勤の翌日は必ず明け、明けの翌日は必ず公休（夜勤→明け→公休）。前日に夜勤がなければ明けは不可。前期末が明けなら今期初日を公休、前期末が夜勤なら今期初日を明け・2日目を公休にする。
- 朝7:00・昼10:00・夕17:45の必要人数を入力・参照できる。初期設定は各4人。日曜の朝昼に限り、初期設定で月3日まで1人減らせる。日数0なら緩和しない。朝昼を両方減らしても同じ日なら1日と数える。日付ごとに設定した必要人数は今期だけ有効で、日曜もその人数をそのまま守る。
- 希望休は必ず公休。明けで代用しない。
- 公休は各人の設定日数以上。
- 余分な公休＝実際の公休日数−設定日数。その最大差は初期設定1日以内、画面で完全同数（0日）も選択可。勝手な緩和はしない。長期休暇など特別な事情がある職員は「希望休」で今期だけ比較から外せる。残る職員同士では従来の公平性を守り、比較から外した職員も希望休・最低公休・連勤・夜勤後公休など他の条件はすべて守る。次の期には引き継がない。
- 夜勤資格、金土日の夜勤不可、A残の可否、パートの個別勤務時間を尊重。
- A残は月6回以内、連日不可。前期最終日との連続も確認。
- 連勤上限を尊重。明けは旧アプリと同じく連勤を区切る。`allowConsecutivePlus1`が真なら上限+1を当期中に1回だけ許可。
- パートの週上限は月曜始まり。前期履歴の同じ週も含む。
- `locked` の固定勤務を保持。

旧検証室は職員の形態・勤務時間・連勤+1設定を読み込んだデータから使用します。新スマホ画面では職員設定を編集できます。

3.17の職員一覧には「今期の公休表に入れる」のスイッチがあります。各期のscheduleにローカルIDの `excludedStaff` 配列を保存し、省略時は全員オン。オフの職員は送信する職員・希望休・希望勤務・固定勤務・履歴・公休比較・夜勤後希望の対象からすべて外します。月一覧・印刷・人数・勤務回数・A/B割合・希望確認数も同じ対象者で集計します。登録情報と希望、オフの職員の保存済み勤務は保持し、再作成時も消しません。切り替えは今期だけで、ほかの期の設定は変えません。前期がオフなら、保持している古い勤務を自動で履歴に使わず、必要な実際の勤務は前期入力で登録します。全員オフなら作成せず職員選択へ案内します。計算APIと必須条件は3.16のままです。

## 公平さと品質の優先順位

3.16では、必須条件を守った表の中で、人数不足→希望休を夜勤後にできない件数→残業合計→朝昼夕の人数超過→残業回数差→比較対象全員の追加公休→残る公休差・残業の偏り・夜勤回数差・A/B割合の偏りの順に評価します。公休差の設定は必須のまま。検査済みの比較元があれば、全員に配れている追加公休の最低値を維持します。同じ人数不足・希望休の例外件数なら、比較元より評価を悪くしません。上位の人数不足や希望休の例外件数を減らせる場合は、残業が増えることがあります。

A/Bは両方できるフルタイム職員の `A/(A+B)` を比較します。目標は対象職員全体の `合計A/(合計A+合計B)` で、50:50に固定しません。各割合を1％単位に丸め、目標との差の合計を減らします。Aのみ・Bのみ・パートは比較から外し、A+Bが0日の職員は目標にも偏りにも影響させません。A残は残業として別に評価します。結果の `allocation.abRatioBalance` に目標割合・職員別割合・偏りの合計を返し、スマホ画面は編集後も現実の表から全体割合を再集計します。

夜勤回数差の1回分は、A/B割合の改善全体より強い重みにしています。検査済みの比較元から追加計算する場合、人数不足と希望休の例外件数が同じ範囲では、夜勤回数差も比較元以下に保ちます（`allocation.preservedNightSpread`）。上位の不足・例外が実際に改善した場合はこの追加制約を適用しません。この制約付きの最適証明は、その範囲での証明です。評価の上限は40人・31日でも整数の64ビット上限内に収まるよう計算し、完成表の独立集計とモデルの評価値の一致を検証します。

3.19では「希望休をできるだけ夜勤後にする」を基本機能とし、職員ごとのチェックとオン・オフを廃止しました。今期の対象者のうち、パート以外で夜勤タイプが「なし」以外の職員全員に自動で適用します。夜勤できない職員とパートの希望休は通常の公休として守ります。APIの既存項目 `nightRestRequiredStaff` は旧バックアップとの互換のため型・登録IDを検査しますが、値は対象職員全員で上書きし、空や一部の指定でもオフにはできません。スマホ画面はこの項目を送信せず、旧保存値も計算・表示に使いません。連続する希望休の最初の日だけを対象に、2日前夜勤→前日明け→当日公休を優先します。希望休当日、直接の希望勤務・希望夜勤、勤務可能日、実際の夜勤後の休みは必須のまま。逆算した夜勤だけが優先希望であり、勤務不可や夜勤人数の衝突を事前確認の不成立理由にしません。

優先希望がある場合は二段階で計算します。第1段階で人数不足（下書きのみ）と希望休の例外件数を減らし、第2段階でその件数を維持して残業等を改善します。巨大な重みの積による整数の上限超過を避けるためです。表が出ない間は第1段階で全時間上限まで探索し、表があれば最大15秒かつ最初の表から3秒を目安に残り時間を配置改善へ回します。最適証明なら早く終了します。二段階を合わせて指定の計算時間内に収めます。

結果と独立検査APIは `nightRestPreferences`（requestedCount、metCount、unmetの職員ID・希望休日・前2日勤務）を返します。生成結果の `minimumUnmetProven` が真なら例外件数が最少。第1段階が未証明なら第2段階が最適でも全体はFEASIBLEとし、最少残業とも説明しません。独立検査だけでは最適性を証明しません。例外日をスマホ画面と印刷に明示し、例外だけではINVALIDや人数不足のDRAFTにしません。3.19の優先方式は `night-rest-default-1`、画面の条件署名はrules-3.19です。旧表と希望を保持して自動で現行条件に再確認し、旧方式の最適証明を新方式の証明として使いません。通常作成の早期終了と追加60秒計算は3.18のまま維持します。

API入力の `fairnessExcludedStaff` は今期の比較から外す職員IDの配列（省略時は空配列）。未知ID、重複、不正な型を拒否します。スマホ保存データでは各期のscheduleにローカルIDで保持し、送信時に匿名IDへ変換します。旧バックアップは全員を比較する従来の動作です。

API `requiredStaff` は朝・昼・夕の必要人数の配列（各0〜40、既定 `[4,4,4]`）。`maxReducedSundays` は日曜の朝昼を1人減らせる最大日数（0〜5、既定3）。`dailyRequiredStaff` は1始まりの期間日番号→必要人数配列（既定空）で、通常設定より優先し日曜緩和も適用しない。スマホの通常設定は全期共通のpreferences、日付ごとの変更は対象期のscheduleに保存する。生成・独立検査・事前確認・日別表示・月一覧・印刷が同じ入力を使う。月一覧と印刷の人数行は「実際/必要」で表示する。

## 人数不足の下書き

APIの厳密な作成は人数不足の表を返しません。`allowStaffingShortfall: true` を指定した場合は、朝・昼・夕の必要人数を不足可として探索します。最優先で各時刻の不足人数の合計を減らし、その後に公休・勤務バランスを評価します。夜勤資格、希望休、連勤、夜勤→明け→公休、最低公休、週上限、A残上限、固定勤務、公休の比較対象内の公平性は必須のまま。それらが矛盾する場合は人数不足の表も作れません。

3.13以降のスマホ画面は通常の作成・再作成・追加計算で `allowStaffingShortfall: true` と `allowNightShortfall: true` を明示して送ります。画面の下書き専用操作と手動検査ボタンは廃止し、不足も表示した公休表として出力します。APIは両指定なしの厳密な作成も従来どおり受け付けます。`allowNightShortfall` は `allowStaffingShortfall: true` と組み合わせた場合だけ有効です。夜勤を0人または1人にし、埋められない日を夜勤未配置として出します。希望勤務・資格・実際の夜勤→明け→公休・固定勤務は緩めず、夜勤2人は認めません。夜勤未配置も最上位の不足合計に含めます。両フラグを指定しない作成では夜勤1人が必須です。画面と印刷の月一覧に夜勤の「実際/必要」行を表示し、不足日を赤く表示します。3.16のA/B改善でこの不足の扱いは変更していません。

独立検査が人数不足（`coverage`, `sunday_limit`、明示指定時に限り実人数0・必要1の `night_coverage`）以外の違反を検出した表は返さない。不足が残る結果は `DRAFT` とし、`solverStatus`、`unmetConditions`、`staffingShortfallTotal`（日勤と夜勤の不足合計）、`daytimeShortfallTotal`、`nightShortfallTotal`、`shortfallProvenMinimum` を返す。`validationErrors` を空にしない。検査範囲も `DRAFT_WITH_HISTORY` / `DRAFT_PERIOD_ONLY` として区別する。日曜の緩和先はソルバーの変数を流用せず、実人数から減らせる不足が多い日を優先して独立に評価し、上限を超えた日は通常人数に対する不足も明示する。

3.18以降は不足許可でも通常作成の「最初の採用可能な表から10秒後、最低15秒で終了」を適用する。表が見つからない間は上限60秒まで探す。追加計算では早期終了せず上限まで改善を探す。どちらも最適または不成立を証明した場合は早く終了する。すべての必須条件を有効に固定し、4つの探索を使うため、下書きでは通常作成の原因集合抽出を行わない。並行探索の結果は同じシードでも同一とは限らない。同じ入力で下書きを作り直し、不足が増えた場合は、元の不足が少ない下書きを保持する。

画面・月一覧・印刷は不足ありと明記し、日付・時刻または夜勤・実人数・必要人数・不足人数を表示する。下書きを条件を満たす表として表示しない。人数以外の必須条件が守られた下書きは、下書き改善の比較元に限って利用できる。手直し後の確認でも不足が残ればDRAFTを保ち、それ以外の違反はINVALIDとして内容を表示する。希望休を夜勤後にできない場合は別の例外表示とする。時間制限内の下書きの不足が最少であるとは限らず、`shortfallProvenMinimum` が真のときだけ不足合計の最少が証明されている。

最適化が時間切れでも検査済みの表があれば返しますが、「すべてのバランスが最良」とは表示しません。公休超過の差が0なら、公平さの差についてはそれ以上小さくできません。勤務日数を減らしすぎない最適性とは別です。

## 判定の意味

|結果|意味|
|---|---|
|OPTIMAL|登録したモデルの必須条件を満たし、指定した評価値の最適性も確認|
|FEASIBLE|必須条件と独立検査を満たすが、評価値の最適性は未確認|
|INFEASIBLE|入力モデルの条件が同時に成立しないことを確認。表は返さない|
|UNKNOWN|時間内に解または不成立の証明を得られなかった。表は返さない|
|INVALID_INPUT|形式や範囲が不正。計算しない|
|VALIDATION_FAILED|生成後の独立検査で違反を検出。表は返さない|

`conflictGroups`は十分な矛盾条件群で、最小の原因集合ではありません。現状は条件が多数列挙される場合があり、「どこを変えればよいか」の最小変更提案は未実装です。

## 期間境界と未確認事項

`history`は各職員の前期末尾7日分（古い順）。未入力の職員は試験上のみ全休と仮定します。全員分がなければ `PERIOD_ONLY` であり、実際の勤務との境界の合格とは扱いません。不成立もこの仮定の下での判定です。

`carryForward`に末尾7日と翌期冒頭の必須勤務を返します。最終日が夜勤なら `nextDays` は `['nightOff', 'off']`、最終日が明けなら `['off']`。既存の `nextDay` も維持します。翌期の全条件まで先読みして成立を保証するものではありません。

現場の完成済み勤務表との照合はまだです。休憩中の人数、全時刻の人数、資格別配置、遅番翌日の早番禁止、労働時間・契約別の上限等は既存ルールにないためモデル化していません。明けを連勤に数えるか、公平さを全職員で比較してよいかも、実運用前に確認が必要です。

## 再現手順（開発用）

Python 3.12 / OR-Tools 9.15.6755。新しい環境では以下を実行します。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r solver/requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s solver/tests -v
.\.venv\Scripts\python.exe -m solver.benchmark
.\.venv\Scripts\python.exe -m solver.server
```

CLIは `python -m solver.engine input.json --output result.json --seconds 15`。`--feasibility-only`は勤務バランスの最適化を省きますが、公平さの上限を含む必須条件と独立検査は省きません。

入力は既存の職員配列に `year`, `month`, `requests`（1始まりの期間日番号）、任意で `locked`（職員ID→期間日番号→シフト）、`history`、`maxExtraOffSpread` を追加したものです。検証時に生成される `results/case-*.json` の `input` を参照してください。個別の結果データはGitHub・公開サイトへ含めません。

公開版は `public/` のスマホ画面から `api/schedule.py` を呼び出します。職員名を除いて計算条件を送信し、サーバーに表は保存しません。3.18のスマホ画面は通常作成で `seconds: 60, adaptive: true`、追加計算で `seconds: 60, adaptive: false` を送ります。通常作成は不足許可でも「15秒かつ最初の採用可能な表から10秒」で早期終了し、候補がない場合は最大60秒まで探します。追加計算は上限60秒まで改善を探します。どちらも最適または不成立を証明できれば早く返します。早期終了では全段階に共通の開始時刻と最初の候補時刻を使い、夜勤後希望の第2段階でも待ち時間をリセットしません。検査済みの元の表がある場合は開始時点から候補として数え、新しい候補が出なくても元の表を返せます。結果の `seconds` は探索時間、`timing` は方式・上限・終了理由、`stopRule` は早期終了の設定と最初の候補時刻を記録します。画面にも方式・探索時間・終了理由を表示します。独立検査済みの表は初期候補とし、時間切れなら元の表を保持します。表がないまま時間切れになった後の再計算は、`seed`（1〜1000）を変えて探す順番を変えます。検証室は引き続きPC内で動きます。公開版と同じ画面の確認は `python -m solver.app_server`（8766番）です。

旧ブラウザデータは新しい保存領域に引き継ぎます。バックアップ読み込み・手直し・条件変更後は自動で再確認します。前期7日未入力は必ず下書き扱い。公開APIは1回最大60秒、40人、入力400KBに制限します。認証はありません。アクセス増加時には利用制限の追加が必要です。
