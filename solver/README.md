# 公休表の生成処理・スマホ画面

CP-SATで期間全体を組み、独立した検査を通った表だけを返します。新しいスマホ画面は `public/`、公開用の計算窓口は `api/schedule.py` です。旧ブラウザ保存領域は上書きしません。開発開始時の基準コミットは `dabcc76d3c63c01fedfc0fcd6753b58f8d2bc4a9` です。

## 3.29 連休の必須回数

職員設定に「指定なし／月1回以上／月2回以上」を追加。通常・おまかせの共通必須条件で、2日以上の公休のまとまりを1回とする。3〜4連休も1回、希望休は含め、明けは含めない。今期16日〜翌月15日内の公休だけを数える。勤務表の手直し後にも実際の回数・日付を表示し、独立検査では不足を必須違反として扱う。

入力`staff[].minConsecutiveRest`は整数0〜2で省略時0。連休開始日の真偽変数は「当日と翌日が公休、かつ今期の前日が公休でない」を双方向に表し、長い連休を重複して数えない。期間初日だけ前期の勤務を開始判定に使わない。独立検査・画面では表の区間を直接数え、結果に`consecutiveRest`を任意追加する。診断だけは不足を許して説明するが、完成表は必須回数を緩和しない。

指定なしでは従来のモデル・送信・署名を維持する。正の指定時だけ署名`rules-3.29`／`auto-rules-2`。方式・優先順・最大時間は3.28と同じ。画面・API3.29、アセットv41。保存時の連休条件・バックアップ・コピーに対応。数え方と診断の詳細は`連休必須.md`、実測とテストは`検証結果.md`。

画面でテストケースを選び「条件を読み込む」→必要に応じて公休・夜勤・希望休などを変更→「この条件で検証する」。条件と結果はJSONで保存できます。本番アプリの書き出しも読み込めます。対象月を選んでから読み込むと、その月の希望休と、前期の末尾7日分があれば取り込みます。既存の当期勤務は固定扱いにせず、白紙から再生成します。

## 守る条件

- 期間は指定月16日〜翌月15日。1人1日1区分。
- 毎日夜勤1人。夜勤の翌日は必ず明け、明けの翌日は必ず公休（夜勤→明け→公休）。前日に夜勤がなければ明けは不可。前期末が明けなら今期初日を公休、前期末が夜勤なら今期初日を明け・2日目を公休にする。
- 朝7:00・昼10:00・夕17:45の必要人数を入力・参照できる。初期設定は各4人。日曜の朝昼に限り、初期設定で月3日まで1人減らせる。日数0なら緩和しない。朝昼を両方減らしても同じ日なら1日と数える。日付ごとに設定した必要人数は今期だけ有効で、日曜もその人数をそのまま守る。
- 希望休は必ず公休。明けで代用しない。
- 公休は各人の設定日数以上。通常版で「固定」を選んだ職員は指定日数ちょうど（明けは含めない）。
- 余分な公休＝実際の公休日数−設定日数。その最大差は初期設定1日以内、画面で完全同数（0日）も選択可。勝手な緩和はしない。長期休暇など特別な事情がある職員は「希望休」で今期だけ比較から外せる。残る職員同士では従来の公平性を守り、比較から外した職員も希望休・最低公休・連勤・夜勤後公休など他の条件はすべて守る。次の期には引き継がない。
- 夜勤資格、金土日の夜勤不可、A残の可否、パートの個別勤務時間を尊重。
- A残は月6回以内、連日不可。前期最終日との連続も確認。
- 連勤上限を尊重。明けは旧アプリと同じく連勤を区切る。`allowConsecutivePlus1`が真なら上限+1を当期中に1回だけ許可。
- パートの週上限は月曜始まり。前期履歴の同じ週も含む。
- `locked` の固定勤務を保持。

旧検証室は職員の形態・勤務時間・連勤+1設定を読み込んだデータから使用します。新スマホ画面では職員設定を編集できます。

3.17の職員一覧には「今期の公休表に入れる」のスイッチがあります。各期のscheduleにローカルIDの `excludedStaff` 配列を保存し、省略時は全員オン。オフの職員は送信する職員・希望休・希望勤務・固定勤務・履歴・公休比較・夜勤後希望の対象からすべて外します。月一覧・印刷・人数・勤務回数・A/B割合・希望確認数も同じ対象者で集計します。登録情報と希望、オフの職員の保存済み勤務は保持し、再作成時も消しません。切り替えは今期だけで、ほかの期の設定は変えません。前期がオフなら、保持している古い勤務を自動で履歴に使わず、必要な実際の勤務は前期入力で登録します。全員オフなら作成せず職員選択へ案内します。計算APIと必須条件は3.16のままです。

## 公平さと品質の優先順位

3.22では、必須条件を守った表の中で、人数不足合計→夜勤未配置→希望休を夜勤後にできない件数→夜勤回数差→残業合計→朝昼夕の人数超過→残業回数差→比較対象全員の追加公休→残る公休差・残業の偏り・A/B割合の偏りの順に評価します。公休差の設定は必須のまま。検査済みの比較元があれば、全員に配れている追加公休の最低値を維持します。同じ上位条件なら比較元より評価を悪くしません。人数不足・夜勤未配置・希望休の例外件数・夜勤回数差を減らせる場合は、残業が増えることがあります。

A/Bは両方できるフルタイム職員の `A/(A+B)` を比較します。目標は対象職員全体の `合計A/(合計A+合計B)` で、50:50に固定しません。各割合を1％単位に丸め、目標との差の合計を減らします。Aのみ・Bのみ・パートは比較から外し、A+Bが0日の職員は目標にも偏りにも影響させません。A残は残業として別に評価します。結果の `allocation.abRatioBalance` に目標割合・職員別割合・偏りの合計を返し、スマホ画面は編集後も現実の表から全体割合を再集計します。

第1段階で人数不足・夜勤未配置・希望休の例外件数・夜勤回数差を小さな整数の辞書式評価で決定し、その値を固定して第2段階で残業や配置を改善します。夜勤回数差を日勤や残業の改善で広げません。夜勤対象は今期のパート以外の夜勤可能者全員です。30日・6人なら差0、31日・6人なら差1が理想ですが、希望勤務・曜日制限・前期履歴などを緩めて強制することはしません。上位条件と共存できる最小差を探し、未証明の差を「数学的に必要」と表示しません。検査済みの比較元から追加計算する場合も同じ優先順位と追加公休維持の範囲で比較します。`nightFairness` は職員別回数・差・算術上の最小差・証明状態・範囲・理由を返します。`reason=constraints` は優先段階の最適性が証明された場合のみで、時間切れなら `not_proven` です。評価の上限は40人・31日でも整数の64ビット上限内に収まります。

3.19では「希望休をできるだけ夜勤後にする」を基本機能とし、職員ごとのチェックとオン・オフを廃止しました。今期の対象者のうち、パート以外で夜勤タイプが「なし」以外の職員全員に自動で適用します。夜勤できない職員とパートの希望休は通常の公休として守ります。APIの既存項目 `nightRestRequiredStaff` は旧バックアップとの互換のため型・登録IDを検査しますが、値は対象職員全員で上書きし、空や一部の指定でもオフにはできません。スマホ画面はこの項目を送信せず、旧保存値も計算・表示に使いません。連続する希望休の最初の日だけを対象に、2日前夜勤→前日明け→当日公休を優先します。希望休当日、直接の希望勤務・希望夜勤、勤務可能日、実際の夜勤後の休みは必須のまま。逆算した夜勤だけが優先希望であり、勤務不可や夜勤人数の衝突を事前確認の不成立理由にしません。

優先希望がある場合は二段階で計算します。第1段階で人数不足（下書きのみ）と希望休の例外件数を減らし、第2段階でその件数を維持して残業等を改善します。巨大な重みの積による整数の上限超過を避けるためです。表が出ない間は第1段階で全時間上限まで探索し、表があれば最大15秒かつ最初の表から3秒を目安に残り時間を配置改善へ回します。最適証明なら早く終了します。二段階を合わせて指定の計算時間内に収めます。

結果と独立検査APIは `nightRestPreferences`（requestedCount、metCount、unmetの職員ID・希望休日・前2日勤務）を返します。生成結果の `minimumUnmetProven` が真なら例外件数が最少。第1段階が未証明なら第2段階が最適でも全体はFEASIBLEとし、最少残業とも説明しません。独立検査だけでは最適性を証明しません。例外日をスマホ画面と印刷に明示し、例外だけではINVALIDや人数不足のDRAFTにしません。3.19の優先方式は `night-rest-default-1`、画面の条件署名はrules-3.19です。旧表と希望を保持して自動で現行条件に再確認し、旧方式の最適証明を新方式の証明として使いません。通常作成の早期終了と追加60秒計算は3.18のまま維持します。

API入力の `fairnessExcludedStaff` は今期の比較から外す職員IDの配列（省略時は空配列）。未知ID、重複、不正な型を拒否します。スマホ保存データでは各期のscheduleにローカルIDで保持し、送信時に匿名IDへ変換します。旧バックアップは全員を比較する従来の動作です。

API `requiredStaff` は朝・昼・夕の必要人数の配列（各0〜40、既定 `[4,4,4]`）。`maxReducedSundays` は日曜の朝昼を1人減らせる最大日数（0〜5、既定3）。`dailyRequiredStaff` は1始まりの期間日番号→必要人数配列（既定空）で、通常設定より優先し日曜緩和も適用しない。スマホの通常設定は全期共通のpreferences、日付ごとの変更は対象期のscheduleに保存する。生成・独立検査・事前確認・日別表示・月一覧・印刷が同じ入力を使う。月一覧と印刷の人数行は「実際/必要」で表示する。

## 人数不足の下書き

APIの厳密な作成は人数不足の表を返しません。`allowStaffingShortfall: true` を指定した場合は、朝・昼・夕の必要人数を不足可として探索します。最優先で各時刻の不足人数の合計を減らし、その後に公休・勤務バランスを評価します。夜勤資格、希望休、連勤、夜勤→明け→公休、最低公休、週上限、A残上限、固定勤務、公休の比較対象内の公平性は必須のまま。それらが矛盾する場合は人数不足の表も作れません。

3.13以降のスマホ画面は通常の作成・再作成・追加計算で `allowStaffingShortfall: true` と `allowNightShortfall: true` を明示して送ります。画面の下書き専用操作と手動検査ボタンは廃止し、不足も表示した公休表として出力します。APIは両指定なしの厳密な作成も従来どおり受け付けます。`allowNightShortfall` は `allowStaffingShortfall: true` と組み合わせた場合だけ有効です。夜勤を0人または1人にし、埋められない日を夜勤未配置として出します。希望勤務・資格・実際の夜勤→明け→公休・固定勤務は緩めず、夜勤2人は認めません。夜勤未配置も最上位の不足合計に含めます。両フラグを指定しない作成では夜勤1人が必須です。画面と印刷の月一覧に夜勤の「実際/必要」行を表示し、不足日を赤く表示します。3.16のA/B改善でこの不足の扱いは変更していません。

独立検査が人数不足（`coverage`, `sunday_limit`、明示指定時に限り実人数0・必要1の `night_coverage`）以外の違反を検出した表は返さない。不足が残る結果は `DRAFT` とし、`solverStatus`、`unmetConditions`、`staffingShortfallTotal`（日勤と夜勤の不足合計）、`daytimeShortfallTotal`、`nightShortfallTotal`、`shortfallProvenMinimum` を返す。`validationErrors` を空にしない。検査範囲も `DRAFT_WITH_HISTORY` / `DRAFT_PERIOD_ONLY` として区別する。日曜の緩和先はソルバーの変数を流用せず、実人数から減らせる不足が多い日を優先して独立に評価し、上限を超えた日は通常人数に対する不足も明示する。

3.18以降は不足許可でも通常作成の「最初の採用可能な表から10秒後、最低15秒で終了」を適用する。表が見つからない間は上限60秒まで探す。追加計算では早期終了せず上限まで改善を探す。どちらも最適または不成立を証明した場合は早く終了する。すべての必須条件を有効に固定し、4つの探索を使うため、下書きでは通常作成の原因集合抽出を行わない。並行探索の結果は同じシードでも同一とは限らない。同じ入力で下書きを作り直し、不足が増えた場合は、元の不足が少ない下書きを保持する。

画面・月一覧・印刷は不足ありと明記し、日付・時刻または夜勤・実人数・必要人数・不足人数を表示する。下書きを条件を満たす表として表示しない。人数以外の必須条件が守られた下書きは、下書き改善の比較元に限って利用できる。手直し後の確認でも不足が残ればDRAFTを保ち、それ以外の違反はINVALIDとして内容を表示する。希望休を夜勤後にできない場合は別の例外表示とする。時間制限内の下書きの不足が最少であるとは限らず、`shortfallProvenMinimum` が真のときだけ不足合計の最少が証明されている。

最適化が時間切れでも検査済みの表があれば返しますが、「すべてのバランスが最良」とは表示しません。公休超過の差が0なら、公平さの差についてはそれ以上小さくできません。勤務日数を減らしすぎない最適性とは別です。

## 判定の意味

|結果|意味|
|---|---|
|OPTIMAL|登録したモデルの必須条件を満たし、指定した評価値の最適性も確認|
|FEASIBLE|必須条件と独立検査を満たすが、評価値の最適性は未確認|
|INFEASIBLE|入力モデルの条件が同時に成立しないことを確認。表は返さない|
|UNKNOWN|時間内に解または不成立の証明を得られなかった。表は返さない|
|INVALID_INPUT|形式や範囲が不正。計算しない|
|VALIDATION_FAILED|生成後の独立検査で違反を検出。表は返さない|

`conflictGroups`は十分な矛盾条件群で、最小の原因集合ではありません。現状は条件が多数列挙される場合があり、「どこを変えればよいか」の最小変更提案は未実装です。

## 期間境界と未確認事項

`history`は各職員の前期末尾7日分（古い順）。未入力の職員は試験上のみ全休と仮定します。全員分がなければ `PERIOD_ONLY` であり、実際の勤務との境界の合格とは扱いません。不成立もこの仮定の下での判定です。

`carryForward`に末尾7日と翌期冒頭の必須勤務を返します。最終日が夜勤なら `nextDays` は `['nightOff', 'off']`、最終日が明けなら `['off']`。既存の `nextDay` も維持します。翌期の全条件まで先読みして成立を保証するものではありません。

現場の完成済み勤務表との照合はまだです。休憩中の人数、全時刻の人数、資格別配置、遅番翌日の早番禁止、労働時間・契約別の上限等は既存ルールにないためモデル化していません。明けを連勤に数えるか、公平さを全職員で比較してよいかも、実運用前に確認が必要です。

## 3.21 作業結果と明示保存

作成結果はブラウザの作業用データです。通常作成には initialAssignments を送らず、60秒の改善計算だけに表示中の結果を送ります。公休の必須条件、夜勤・残業・A/Bの評価、希望休を夜勤後にする方針は変更しません。失敗時に古い表を新しい結果として表示しません。条件変更で作業結果をリセットします。

- 不足として出す：朝昼夕の必要人数、日曜の緩和日数。

**段階の止め方**：条件（例外→人数不足→夜勤後の希望休→夜勤回数差）→残業→配置の各段階は、最少と証明できたとき、または一定時間良くならなかったとき（条件60秒・残業40秒・配置30秒）に、その値より悪くしない条件を付けて次へ進む。秒数は2026年10月の実測（偽名11人の設定・5条件）で、改善の間隔が最大で条件26秒・残業21秒・配置9秒だったこと、人数不足が出る月は条件段階で30秒以上空いてから不足が減った例があったことによる。夜勤を必須にすると、不足のない月の条件段階は数秒で証明できる。1回の呼び出しは60秒以内のままで、途中なら `search.resume`（段階・最後に良くなってからの秒数・証明済みの段階）を返し、画面は最良の表と `resume` を渡して続きを自動で呼ぶ。全段階が終われば `search.done: true`。全体の上限は5分。続きの計算では、途中の表の追加公休を固定しない（利用者の「さらに改善する」では従来どおり固定）。

## 3.25 残業合計を増やさず回数差を最少化

利用者は、残業が6・4・3回などに偏ることを問題とし、「残業合計を増やさず、回数差を最小にする」を選択した。残業の合計最少化に続けて`overtime_fairness`段階を追加し、A残可能なフルタイム職員間の最大回数−最小回数を小さくする。人数超過の削減より先に扱う。評価重みと画面の最良候補比較をともに、残業合計→残業回数差→人数超過→追加公休→細部へ変更した。

条件→残業合計→残業回数差→配置の4段階。停滞上限は60／40／30／30秒。公平化の30秒は初期設定で、3.24時の3段階の実測から直接証明された値ではない。1通信60秒、探索合計300秒の上限は維持する。段階の再開・証明に`overtime_fairness`を追加し、証明済みの最少残業合計は後続で固定する。残業合計が未証明でも、公平化・配置で現在候補の合計を増やさない。

`overtimeFairness`は`byStaff,total,spread,idealSpread,minimumSpreadProven,scope,reason`を返す。算術理想は合計が比較人数で割り切れると0、それ以外1。理想に到達した場合は同じ合計でこれ以上均等にはできない。差が理想より大きい場合、上位条件・残業合計・公平化段階の証明がそろったときだけ`reason=constraints`、それ以外は`not_proven`とする。最少証明は人数不足・希望休の夜勤後配置・夜勤回数などの上位条件と残業合計を維持した範囲であり、未登録の現場ルールや条件変更後まで保証しない。改善元がある場合は、維持した追加公休も証明範囲に含む。

画面は残業可能者の実際の回数・差を再集計し、同じ合計での算術理想、条件下の最少確認済み、未確認を分けて表示する。編集後や旧方式の保存表に新方式の証明を転用しない。悪化応答・通信失敗でも公平な候補を保持し、同じ品質なら既存の公平性の証明を保持する。

架空条件の検証：合計13回を6・4・3から4・4・5へ分散し、合計増なし・必須違反なし。6回の希望勤務を強制した条件では差3が最少と証明できる。架空11人3月の3.24候補（残業29、差3）から公平化段階を60秒以内で追加実行した例では、52.242秒で残業28・7人全員4回・人数超過11、人数不足0・夜勤差1・必須違反なしを得た。残業合計28の最少は未証明。白紙から別々に120秒以内で比較した試案では29対31となっており、上記の改善を新規作成の毎回の保証や同時間比較としない。

## 3.26 出勤できる日数が少ない人の残業

希望休が公休の最低日数を超える人（長期休暇など）について、出勤できる日数＝期間日数−max(公休の最低日数, 希望休の日数) を、普通の出勤日数＝期間日数−公休の最低日数 と比べる（`input_data.overtime_profile`）。

- A残の上限：min(6, ⌈6×出勤できる日数÷普通の出勤日数⌉)。必須条件で、独立検査の `overtime_limit` も同じ上限を使い `actual`・`limit` を返す。
- 残業回数の比較：比率で比べる人がいる月は、普通の人の係数100、少ない人は100×普通÷出勤できる日数（四捨五入、600まで）で換算した回数の最大−最小を `overtime_fairness` 段階で最小化する（`allocation.overtime_scales`）。いない月は係数1で、3.25と同じ回数差・同じ重み。重みの上限は40人・31日の最悪でも約1.4e17。
- `metrics` の `overtimeSpread` は普通の人どうしの回数差（画面表示用）、`overtimeBalance` は換算後の差（計算・候補比較用）、`overtimeIdealBalance` は全員が普通の人のときの算術上の最少、`overtimeProportional` は比率の人の有無。
- 結果の `overtimeFairness.proportionalStaff` に、比率で比べた人の出勤できる日数・普通の日数・上限を返す。比率の人がいる場合 `idealSpread` は null で、最少は計算で証明できたときだけ表示する。

## 3.27 残業の公平化と計算の再開

公開3.26では、実入力の通常作成で約206秒・残業23回・回数差5回となった。公平化は30秒でUNKNOWNのまま停滞終了していた。勤務だけのヒントでは回数・人数・A/B比率などの補助変数を再構築できず、検査済みの表からの再開にも時間が掛かっていた。

## 3.30 通常版の残業歓迎

`staff[].overtimePreference`（整数0〜2、省略時0）は通常／少し多め（＋1回目安）／多め（＋2回目安）。残業合計の削減を優先し、その合計を固定して歓迎の目安に沿う配分差を最少化する。比率で換算した回数から上乗せ目安を引いて比較するため、出勤可能日数が少ない人の歓迎分も比率で調整される。絶対上限・希望・固定・連休必須は変えない。

歓迎ありだけ方式`quality-first-6`・署名`rules-3.30`。通常指定だけの入力は従来の方式・署名・計算を維持。おまかせは、ユーザーの指定により今回適用せず、送信と計算入口で歓迎項目を除去する。通常300秒・1通信60秒、おまかせ480秒の時間枠は変更しない。

配分の算術下限は整数回数・各人の上限・固定合計を含めて正確に求め、日付制約も含む探索での証明と分けて扱う。合計が最少との証明と、同じ合計での配分の最少証明を混同しない。詳細は[残業歓迎.md](../残業歓迎.md)、測定は[検証結果.md](../検証結果.md)。画面・API3.30、アセットv42。

## 3.38 連休なし

職員の `noConsecutiveRest`（真偽値、既定 false、`minConsecutiveRest` と同時指定不可）。前日・当日がともに公休の組を1件と数える（`rest_blocks.forbidden_pairs`）。明けは休みに数えない。両日とも希望休・固定の公休・前期の実績なら数えない。前期最終日は、実際に入力された前期の勤務（`p['historyProvided']`）が公休のときだけつなげる。

- 独立検査：連続ごとに `no_consecutive_rest`（`start`・`end`・`count`）。中間ルールの例外として扱うが、`exception_count` には含めず `rest_exception_count` で別に数える。
- 画面からの作成（`allowRuleExceptions: true`）：通信ごとに最初に連休の数だけを最小化し（最大20秒）、最適が証明できたらその値を上限に固定してから通常の段階探索に進む。証明できなければ `UNKNOWN`（表なし・継続推奨）。最少を超える例外の表も `UNKNOWN`。結果に `noConsecutiveRest`（minimum・proven・seconds）、例外があれば `restExceptionCount`・`restExceptionsProvenMinimum`。
- 厳密な作成・おまかせ：連休0件を必須条件にする。理由調べ：中間ルールと同じ最下位で許す。

## 3.39 夜勤の端数優先

職員の `nightRemainderPriority`（真偽値、既定 false、夜勤できるフルタイムだけ有効）。基準＝期間日数÷夜勤できる人数、端数＝余り、目安＝優先の人は基準＋1・ほかは基準。目安を超えた夜勤の合計（超過）から、許容量 max(0, 端数−優先人数) を引いた分が例外（`night_remainder.report`）。

- 独立検査：例外があるときだけ、目安を超えた人ごとに `night_remainder`（actual・fair・count・priority・exceptions）。中間ルールの例外だが `exception_count` には含めない。
- 画面からの作成：連休なしの証明の後、通信ごとに超過の最少を証明して上限に固定（連勤などの例外0件の範囲で最大5秒→だめなら例外を許して合計最大20秒）。証明できなければ `UNKNOWN`。最少を超える表も `UNKNOWN`。補助として1人ずつの夜勤の最大回数（`max_nights`）を上限に加える。
- 結果：`nightRemainder`、例外があれば `nightRemainderExceptions`。厳密な作成では超過≤許容量を必須、理由調べでは最下位で許容。おまかせでは `without_preferences` で除去。

## 3.40 A残は1回の出勤サイクルに1回

入力の `overtimeCycleLimit`（真偽値、既定 false。通常版の画面が常に true を送る。おまかせでは `without_preferences` で除去）。出勤サイクル＝公休・明けで区切った出勤のひと続き（夜勤を含む）。日ごとに、A残の日はそのサイクルに既にA残があれば1件。希望勤務・固定のA残も数える（`overtime_cycles.report`、画面は `OvertimeCycles.scan`。`wishOnly` はサイクルの今期のA残がすべて希望・固定）。前期の実績が入力されていれば、最後の公休・明けより後のA残を今期1日目のサイクルへ持ち越す。

- 計算：職員・日ごとに「このサイクルにA残がある」の状態変数（0/1、等式で確定）と2回目の変数を置く。条件段階の優先順位で 人数不足 → 夜勤未配置 → **2回目の件数** → 夜勤後の希望休 → 夜勤回数差。係数 `cycle_weight=(希望休の評価数+1)×preference_weight`、その上の `gap_weight=(各人のA残上限の合計+1)×cycle_weight`。最少の事前証明はしない（人数不足が上位なので、2回目を入れるのは人数不足を減らすときだけ）。
- 結果：`overtimeCycleExcess` と `overtimeCycles`（excess・items[staff, start, end, overtime, count, wishOnly]・minimumProven＝条件段階の証明）。候補の比較（`creation-workflow.js`）も同じ順。方式 `quality-first-8`。

## 3.44 採用表に対応する最少判定

途中で上位条件が改善した場合、次の段階にも最新の評価値の上限を付ける。候補を総合比較で不採用にしてもソルバーのOPTIMALだけで最少判定を付けていた処理を修正し、採用表の評価値と最適値が一致した場合だけ証明する。不一致なら段階を未確認として継続する。

継続状態の`resume.proofValues`は、各段階をキーとする配列。conditionsなら条件値、overtimeなら条件値と合計、overtime_fairnessならさらに配分の差、placementならさらに総合評価を含む。存在しない評価式はnull。次の通信で採用表の値と照合し、値が変わった証明・数値を持たない旧証明を取り消す。入力では段階名・長さ・非負整数またはnullを検査する。

## 3.46 連休の回数の差

入力の `restCountBalance`（真偽値、既定 false。通常版の画面が、連休の設定をした人が今期にいるときだけ true を送る。おまかせでは `without_preferences` で除去）。比べる人は `minConsecutiveRest` が1以上で、`fairnessExcludedStaff` にいない人（2人以上のときだけ）。数える連休は、今期内の2日以上続く公休のうち、計算が決めた公休を1日でも含むもの（`rest_blocks.counted_ranges`、画面は `ConsecutiveRest.counted`）。最大−最小が1を超えた分が例外（`rest_blocks.balance_report`）。

- 計算：数える回数＝連休の始まりの数−「前後の日が公休でない、希望休・固定の公休だけのひと続き（2日以上）」の数。最大・最小の補助変数から超過を作る。画面からの作成では、連休なし・夜勤の端数の証明の後に超過の最少を証明する（例外0件の範囲で最大5秒→例外を許して合計最大20秒、並行8）。証明できなければ `UNKNOWN`。超過は条件段階の優先順位に入れる（`balance_weight`：人数不足などの下位全体の上限より大きく、連勤などの例外の係数より小さい。下限から人数不足を取り出す計算も対応）。上限としては固定しない。
- 表の採用：例外0件の範囲で確かめた最少を超える表は `UNKNOWN`。例外を許して確かめた最少を超える表は採用し、`restBalance.proven=false`。
